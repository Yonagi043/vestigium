# 方法

[English](METHODS.md) · [结果](RESULTS_ZH.md) · [README](../README_ZH.md)

本页讲清[结果](RESULTS_ZH.md)页那次比较是怎么设计的、怎么尽量做到公平，以及你怎样重跑。

## 比较了什么

每道题都在一个新的 Claude Code 会话里回答（2.1.283 版，无界面运行）。各种用法的提示词完全相同，只有说明材料的那一行不同：

| 名字 | 材料 | 工具 |
|---|---|---|
| **T** | Vestigium（迹），只开放这道题用到的文档 | 只能用 Vestigium 的 MCP 工具 |
| **W′** | Docling 提取的整篇文本，存成一个文本文件，长行在句末折开 | Read、Grep、Glob |
| **P** | PDF 文件 | Read、Grep、Glob（Read 把 PDF 页作为图片读入） |
| **V′** | Vestigium 修补过的文本，用同样的方法折行 | Read、Grep、Glob；只在看图题上跑 |

超过 900 秒或者用满 60 轮的运行会被停下，按它当时已有的答案判分。

模型：Claude Haiku 4.5 跑 T、W′（两遍）、P 和 V′；Claude Opus 5.5（推理强度 `xhigh`）在文字题上跑 T 和 W′。Opus 没跑 P，因为事先的小检查里它用 T 和 W′ 都已经是 100%。Opus 也没跑看图题：为了不超预算，这部分在开跑前就砍掉了。

## 公平的整篇文本对照

Vestigium 最直接的替代做法，是把整篇文本交给 AI 助手，让它自己去搜。我们发现，最初的这个对照组吃了亏：

- Claude Code 的 Grep 会把超过 500 字的命中行藏起来（显示成 “Omitted long line”）；
- 我们的文本文件里，一行最长约 1000 字，模型经常看不到自己搜到的那一行。

所以我们做了 W′：还是同样的文本，把长行在句末折开，让每行不超过 400 字（连同折行处保留的空格最多 404 字）；单句超过 400 字时，才在词与词之间折。这离 Grep 的 500 字界线还很远。一个字符都没有删改，去掉新加的换行就能逐字还原原文。正式确认的全部运行里，Grep 藏起来的行数是 **0**。

开发阶段对着没折行的文本测出的数字，我们不再引用。[结果](RESULTS_ZH.md)页上的数字都是和 W′ 比的。

W′ 自己也有一个代价：Grep 结果太大时，Claude Code 会把它转存成文件（Haiku 跑 W′ 时有 22–28 次）。这是外壳本身的限制，也是“整篇文本 + 外壳自带搜索”这种用法在实际中的样子。

T 和 W′ 读到的文本不完全相同：T 用的是修补过的版本（补回丢失的表格文字、隐去放错位置的 OCR 副本）。V′ 就是把修补过的文本做成 W′ 的格式。

## 新题

- **谁出的**：由一个单独的 AI 会话出题。它不参与 Vestigium 的开发，也看不到结果。
- **怎么核对**：每道题都盲答一遍，再对照答案和证据页核对；之后由审查者反过来找歧义和答案错误，最后用脚本检查格式，0 错误。补的那 4 题所在的一批里，有些题按审查意见改了措辞，改后没有重新盲答。
- **有多难**：29 道文字题平均每题约 9 个必答要点，我们以前的题约 6 个。约四分之三要推两步以上，10 道要列出 8 项以上，6 道要用两份文档。
- **保密**：这些题在开发时从没用过，也不公开。它们已经用于这次正式确认，以后不再当作“没人见过的题”使用；以后的确认改用另一批不公开的题，出题时避开了开发题考过的事实。随发布一起提供的是开发题，见[复现](#复现)。
- **和旧题的重叠**：29 道文字题里，有 2 道和旧的开发题考同一批事实，1 道用了同一类陷阱。开跑前就标了出来，主分析包含它们；去掉它们是事先定好的敏感性检查之一。
- **看图题**：18 道看图题也是这样出的，附有给判分用的证据截图。

## 预注册

正式确认的任何一次运行之前，完整的方案就已经写好，提交进了版本库。方案里定死了：

- **要回答的 4 个问题**，只回答这些：
  1. 花费和用时；
  2. 用 Haiku 时 T 比 P 准多少；
  3. 用 Haiku 时 T 是否不比 W′ 差，界限是 **5 个百分点**（主问题）；
  4. 编造。
- **统计方法**：精确检验、区间、随机种子，以及每种可能结果的措辞。不许写“打平”或“相当”。
- **题目**：文件的校验值、先跑哪些题、补题的规则。
- **判分规则**：重判多少、分歧怎么裁决。
- **运行规则**：什么算失败或无效，什么时候整批停下。
- **花费上限**：标价 $120。

对方案的每一处解读和改动，都连同理由记了下来：开跑前定下的解读 14 条，开跑后的改动 4 条，没有一条改变结论。完整的预注册文件不公开，因为里面有保密题的标识；它的判定规则已经概括在本页。开跑前，一位审查者还写下了预测，其中一条是对 Vestigium 不利的：要列出一长串内容的题上，它会输 3 个点以上。这条预测没有成立。

## 运行

- **批次**：3 路同时跑，每次启动间隔 60 秒。每一路有自己的运行目录和 Claude Code 配置，每次运行都是一个新会话。
- **停批**：任何一路遇到限流、拒绝访问或 API 错误，3 路一起停。实际一次也没有发生。
- **审计**：每次运行的工具调用都查过。T 只能用 Vestigium 的工具，其他用法只能用 Read、Grep、Glob。读了答案或别的运行记录的，按全错计。实际一次也没有。
- **白名单**：Vestigium 启动时只开放这道题的文档，T 打不开别的文档。
- **合计**：计划内 228 次，补题 12 次，共 240 次，全部第一次就有效。

## 判分

- **盲评**：每道题一个 Claude Opus 判分代理。这道题的所有答案都交给同一个判分代理，每份答案一张单子，用随机编号、随机顺序，不标明出自哪个模型、哪种用法。判分代理能读这些评分单和这道题文档的全文（看图题另加证据截图），不能再分出自己的子代理。
- **重判**：至少 20% 的答案由新的代理重判。Haiku 重判了所有“被比较的两种用法得分不同”的题，再从其余题里随机抽一些；Opus 随机抽 20% 的题。
- **裁决**：两次判分不一致的要点交给第三个代理。它只看到题目、要点、答案和证据页。
- **计分**：严格分是判为“对”的必答要点所占的比例；宽松分把“部分对”也算对。主分析用首判的严格分，裁决后的结果作为敏感性检查。
- **合判的检查**：同一个判分代理同时判两个模型的答案，可能让判分有偏。事先定好的检查比较了首判和重判，没有触发。

判分模型和答题模型同属一家。对决定结论的要点做人工抽检，已列入计划。

## 分析

- **主问题（T − W′）**：逐题算严格分之差，W′ 取两遍的均值，再求平均。按题重抽样 10,000 次，单侧 97.5% 下界高于 −5 个点，就判“不劣”。精确符号翻转置换检验给出的 p 值只作参考。
- **T − P**：同样是逐题差，文字题和看图题分层重抽样；显不显著看精确检验。
- **花费和用时**：同一批题上 T 的合计除以对方的合计。区间按整份文档重抽样，因为同一份文档上的题不是相互独立的。
- **题数**：前 15 题判完首判后，用逐题差的波动大小（不看方向）算出需要多少题。按这条规则补了 4 题。
- **区间的准确度**：我们的模拟显示，在 30 题左右时，按题重抽样的双侧“95%”区间实际只覆盖约 90%，漏的主要在上界那一侧；用来下结论的单侧下界覆盖 96–97.5%。

分析代码在开跑前就写好、测过、提交了。跑完后，另一个代理用自己写的代码复算主要数字，结果相同。

## 这次测试花了多少

整个正式确认按标价花了 $95.68：事先的小检查 $16.92，240 次运行 $34.88，判分 $43.88（112 个判分代理）。独立复算另花 $1.16。这些都是 Claude Code 自报的标价，不是某个套餐的实际扣费。

## 复现

正式确认的题目继续保密，所以正式确认本身没法重跑。其余的都能重跑：发布时一起提供 **Vestigium 公开开发题**，共 122 题，涉及 30 份公开文档，分 5 套：

| 题集 | 内容 |
|---|---|
| `old57` | 一次更早的比较用过的 57 道测试题，那次比较在[结果](RESULTS_ZH.md)页那次之前，这些题现在已转为开发题、随题包提供。那次更早的比较的数字不在结果页上；结果页里发布前的回归检查又用到了这些题 |
| `dev`、`dev2`、`dev3` | 开发阶段出的文字题 |
| `vis_dev` | 要看图的题 |

题包在仓库的 [`benchmark/`](../benchmark/README_ZH.md) 目录里。里面还有一份下载清单（每份 PDF 的公开来源和 SHA-256；我们不分发 PDF 本身），以及逐步写好全部命令的复现说明 [`REPRODUCE_ZH.md`](../benchmark/REPRODUCE_ZH.md)。

简要步骤：

1. **安装**：`pip install "vestigium[ingest,eval] @ git+https://github.com/Yonagi043/vestigium"`。另外要有 Claude Code（我们用的是 2.1.283）和 poppler-utils（`pdftoppm`、`pdfimages`）。
2. **下载并处理文档**：`vestigium eval fetch-docs` 下载文档并核对校验值，再用它生成的脚本，按题目里用的名字逐份运行 `vestigium ingest`。
3. **准备材料**：`vestigium eval fulltext` 写出整篇文本，`vestigium eval fold` 把它做成 W′，`vestigium eval snapshot` 把 Vestigium 固定下来给 T 用。
4. **运行**：`vestigium eval plan`，然后用 `stage` 和 `headless` 一次跑一个，或者像正式确认那样用 `stage-parallel` 和 `parallel` 3 路并行。
5. **判分和汇总**：`vestigium eval sheets --blind 文件名` 用随机编号写出评分单，解盲用的对照表另存在这个文件里；`grading-queue`、`grader-prompt` 把每道题交给一个新的判分代理；`fill` 记下判分；`summarize`、`compare`、`costs` 出表。

评测时服务注册的名字仍是 `tgl`，和我们的运行一致，这样模型看到的工具名和我们的相同。每次运行都要通过你自己的 Claude Code 调用模型。我们这边，一道题用一种用法，花费从几美分（Haiku 用 Vestigium）到约 30 美分（Haiku 直接读 PDF）不等，另加判分。

结果会有出入：

- 这些题比确认题容易，而且开发时我们看过。
- 我们的测试里，同一道题跑两次，花费相差的中位数是 13–23%。
- Claude Code、Docling 换了版本，行为也会变。
- 有几份公开 PDF 在我们下载之后改过；哪些对不上，下载清单里写明了。
